Timesheet Automation – Administrator Guide

This guide explains how the Timesheet Automation application works, how to operate it day to day, and how to extend it when the organization needs a new document library. It is written for administrators who manage the SharePoint site and document libraries used by the application – no coding knowledge is required to follow it.

The application automatically picks up timesheet PDF files uploaded to SharePoint, sends them to an Intelligent Document Processing (IDP) service for data extraction, and writes the results back into SharePoint – without anyone having to manually open or process each PDF.

Who this guide is for

This guide is aimed at the people who manage the SharePoint libraries the application watches – typically site administrators or team leads responsible for uploading timesheets and reviewing results. A few tasks (changing configuration files, redeploying the application) require a developer or platform engineer; those are called out clearly wherever they come up.

What the Application Does

The application watches one or more SharePoint document libraries for timesheet PDFs, sends each one to an IDP (Intelligent Document Processing) service to extract the timesheet data, and writes the results back into SharePoint automatically. Nobody needs to open, read, or manually key in data from these PDFs.

The end-to-end flow

  1. Upload. Someone uploads one or more timesheet PDFs into a library's 01-Inbound folder.
  2. Pickup. The application scans 01-Inbound – either automatically on a schedule, or when manually triggered (see Triggering the Ingest).
  3. Isolation. Each file found is immediately moved to 02-Processing, so it can't be picked up twice if the application runs again before it's finished.
  4. Submission. The file is sent to the IDP service for data extraction. This happens for every file, one at a time, per library.
  5. Extraction (in the background). IDP processes the document asynchronously – this can take anywhere from seconds to a couple of minutes per file. The application checks back periodically until it's done.
  6. Result.
    • If extraction succeeds: the extracted data is written as a CSV to 03-Output, and the original PDF is moved to 04-Processed (the archive).
    • If extraction fails, or IDP doesn't respond within the allowed time, the original PDF is moved to 99-Error for someone to review.

Multiple libraries, one process

The application isn't limited to one document library. Each business unit or site (for example EKN or FLEET) has its own document library, and every library follows the exact same five-folder pattern. On each run, the application works through every configured library in turn, so files from one library are never mixed up with another's – each library's output always lands back in that same library.

See Document Library & Folder Structure for details on the folders, and Adding or Removing a Document Library if your organization needs to onboard a new site.

What this means for you as an administrator

  • You don't need to do anything after uploading a file to 01-Inbound – the application takes it from there.
  • You can check 03-Output and 04-Processed at any time to see what's already been completed.
  • If something ends up in 99-Error, it means it needs a look – see Troubleshooting & FAQ.
  • The Job Logs list gives you a run-by-run summary without having to open any folder.

Document Library & Folder Structure

Every document library the application watches (for example EKN, FLEET) is set up with the exact same five subfolders. This consistency is what lets the application manage any number of libraries without special-casing any one of them.

The five folders

FolderPurposeWho puts files there
01-Inbound Drop zone for new, unprocessed timesheet PDFs You (or whoever uploads timesheets)
02-Processing Files currently being worked on by the application. A file only stays here for the duration of one processing run. The application, automatically
03-Output The extracted data, as a CSV file, for every successfully processed PDF The application, automatically
04-Processed Archive of original PDFs that were successfully processed The application, automatically
99-Error PDFs that could not be processed – extraction failed, or the request timed out The application, automatically

What's safe to do manually

  • Safe: uploading new PDFs to 01-Inbound.
  • Safe: reading, downloading, or filtering files in 03-Output and 04-Processed – these are your results and archive, and the application never touches them again once they're written.
  • Safe: reviewing files in 99-Error, and moving a corrected file back into 01-Inbound to have it reprocessed on the next run (see Troubleshooting & FAQ).
  • Avoid: manually moving or deleting files inside 02-Processing. The application uses this folder to know which files are currently in flight; interfering with it while a run is in progress can cause a file to be skipped or duplicated.

One library per business unit or site

Each document library represents one business unit (e.g. a company site or division). All of a library's files, output, and archive stay within that same library – the application never writes one library's results into another's folders. If your organization needs to add a new business unit, see Adding or Removing a Document Library.

Classifying Timesheet PDFs

Each document library has three extra columns that can be filled in on a file after it's uploaded. These are for your own organization and filtering – they help you and reviewers find and group timesheets when browsing the library, especially the archive.

The columns

ColumnTypePurpose
PDF Type Choice (Salary / Wages) Identifies whether the timesheet relates to salaried or waged staff
Site Choice (e.g. Plumbing, Office Staff, TI Division, etc.) Identifies which company site or division the timesheet belongs to
Week No. Text The week number the timesheet covers

How and when to use them

  • These fields are optional, not mandatory – a file will still be picked up and processed whether or not they're filled in.
  • They are expected to be filled in after uploading the PDF to 01-Inbound, whenever is convenient.
  • The values you set travel with the file: once a PDF is processed and moved to 04-Processed, the same PDF Type, Site, and Week No. values are still there. This is what makes the archive folder easy to filter and review later – for example, to find every waged timesheet from a given site for a given week.

Important: these columns are for you, not for the application

The automation does not read these columns at all. It picks up a file based purely on its being a PDF in 01-Inbound – it doesn't check, use, or depend on PDF Type, Site, or Week No. in any way. You can fill them in before, during, or after processing, in any order, and it will have no effect on whether or how the file is processed. They exist purely to make the document library easier for people to browse and filter.

Triggering the Ingest

There are two ways files get picked up from 01-Inbound and processed: an automatic schedule, and a manual trigger. Both run the exact same process across every configured document library – the only difference is what starts it.

Automatic (scheduled) runs

The application can run on a recurring schedule (by default, hourly) without anyone doing anything. On each scheduled run, it works through every configured document library in turn, checking each one's 01-Inbound folder for new PDFs.

Whether the schedule is currently turned on, and exactly how often it runs, is an environment-specific setting controlled by the platform/development team. If you're not sure whether the schedule is active in your environment, ask them, or use the Job Logs list – every run, scheduled or manual, adds an entry there, so you can see from the timestamps whether scheduled runs are happening.

Manual trigger

The application also exposes a manual trigger that runs the same process on demand, without waiting for the next scheduled run. This is useful when:

  • You've just uploaded files and don't want to wait for the next scheduled run
  • You're testing that everything is configured correctly after a change
  • The scheduled run is turned off in your environment (e.g. during initial setup)

Triggering it requires calling a specific URL for your environment (ask your development/platform team for the exact address, as this differs between environments). Calling it starts a full run across every configured library, exactly like a scheduled run would.

How to tell a run actually happened

After triggering – manually or on schedule – check the Job Logs list. A new row will appear for each document library, with a timestamp, so you can confirm the run took place and see the outcome at a glance.

Job Logs

Every time the application runs – scheduled or manually triggered – it writes one row per document library to a SharePoint list called Mule IDP Job Logs. This is the fastest way to see what happened on a run without opening any folder.

Columns

ColumnMeaning
TitleLibrary name and run timestamp, e.g. EKN_2026-08-19T14:37:13
ExecutionTimeWhen this run for this library happened
SourceFolderWhich document library this row is about (e.g. EKN, FLEET)
ExecutionTypeScheduled or Manual – how the run was started
FilesProcessedHow many files were successfully submitted for processing
ErrorCountHow many files failed during submission
StatusSuccess, Partial Success, or Failed – see below
DetailsFile names that were processed, and/or error messages for any that failed

Making sense of Status

  • Success – every file found in that library's 01-Inbound was submitted without error. This includes the case where there were no files at all – you'll see FilesProcessed = 0 and Details = "No files found". That's expected, not a problem – it just confirms the run happened and the folder was empty.
  • Partial Success – some files were submitted successfully, but at least one failed. Check the Details column for which file(s) failed and why; the failed file(s) will be in 99-Error.
  • Failed – the run for that library couldn't even get started (for example, SharePoint was temporarily unreachable). No files were processed at all in this case. Check Details for the reason, and try again later or contact your development team if it keeps happening.

Important limitation

A row in this list only tells you that a file was successfully handed off to the IDP service for data extraction – it does not yet tell you whether the extraction itself ultimately succeeded. That result shows up later, per file, as the file lands in either 03-Output/04-Processed (success) or 99-Error (failure) – see Document Library & Folder Structure. In short: use the Job Logs list to confirm a run happened and see a quick summary, and use the folders to see the true final outcome for a specific file.

Adding or Removing a Document Library

When a new business unit or site needs to start using the application, a new document library needs to be set up in SharePoint and then registered with the application. This is a joint task – some steps are yours, and one step needs your development/platform team.

Step-by-step

  1. Create the document library. In SharePoint, create a new document library named after the new business unit or site (e.g. matching the style of existing libraries like EKN or FLEET).
  2. Create the five standard folders inside it, using the exact same names as every other library: 01-Inbound, 02-Processing, 03-Output, 04-Processed, 99-Error. See Document Library & Folder Structure for what each one is for. The names must match exactly – the application looks for these folders by name.
  3. (Recommended) Add the same classification columns used elsewhere – PDF Type, Site, Week No. – if you want the new library to be filterable the same way. See Classifying Timesheet PDFs.
  4. Grant the application's service account access to the new library (see Permissions & Access).
  5. Ask your development/platform team to register the new library. This is a configuration change (adding the library's name to a settings file) that requires a deployment – it is not something that can be done from SharePoint alone. Give them the exact library name you used in step 1.

Once your development team confirms the change is deployed, the new library will be picked up automatically on the next scheduled or manually triggered run – no further action needed on your side.

Removing a library

Removing a library from active use is the reverse of step 5 above – ask your development team to remove it from the same settings file and redeploy. The document library itself and its historical files in SharePoint are not deleted by this; it simply stops being scanned for new files.

Configuration Reference

The application's behavior is controlled by a set of settings that live in configuration files deployed alongside it – not in SharePoint. This page is a reference for what those settings control, so you know what to ask for when something needs to change. Changing any of them requires your development/platform team and a redeployment; none of this is self-service from SharePoint.

Settings you may need to reference or ask about

List of document librariesWhich libraries the application scans on every run (see Adding or Removing a Document Library)
Folder namesThe names of the five standard folders (Inbound, Processing, Output, Processed, Error) – these are shared by every library

Environments

The application can be deployed to more than one environment (for example, development, test, and production). Settings can differ between environments – for example, the schedule might be turned off in a test environment but on in production. If you're unsure what's active in the environment you're working with, ask your development/platform team rather than assuming it matches another environment.

Credentials

The application authenticates to SharePoint and to the IDP service using credentials that are stored securely alongside the other settings, not visible in SharePoint itself. You should never need to handle these directly; if access needs to be rotated or an integration stops authenticating, that's a task for your development/platform team.

Permissions & Access

Two different kinds of access are relevant to this application: the access the application itself needs to work with SharePoint, and the access people need to use and manage it.

What the application needs

The application connects to SharePoint using its own dedicated service account/app identity – it does not use any individual person's login. For every document library it manages, this identity needs enough permission to:

  • List and read files in 01-Inbound
  • Move files between all five folders (Inbound → Processing → Output/Processed/Error)
  • Create new files (the extracted CSV) in 03-Output

In practical SharePoint terms, this means Edit/Contribute access on each document library the application manages. It also needs Contribute access on the Mule IDP Job Logs list, since it creates a new item there on every run.

When onboarding a new library (see Adding or Removing a Document Library), granting this same access to the application's identity on the new library is one of the required setup steps.

What people need

TaskSuggested access level
Uploading timesheets, filling in classification columns, reviewing Output/Processed/Error Standard library Read/Contribute access, same as any other SharePoint library
Viewing the Job Logs listRead access to the list
Triggering a manual runRestricted to administrators/developers – this calls an internal application endpoint, not a SharePoint permission
Changing configuration (libraries, schedule, timeouts, etc.)Restricted to the development/platform team – requires a deployment, not a SharePoint permission

As a general rule: anyone who works with timesheets day to day only needs ordinary access to the document libraries and the Job Logs list. Anything that changes how the application behaves should go through your development/platform team.

Troubleshooting & FAQ

"I uploaded a PDF, but it doesn't seem to have been picked up"

  • Check the file is actually a .pdf and was uploaded directly into 01-Inbound (not a subfolder).
  • Check Job Logs for a recent run on that library – if the most recent run happened before you uploaded, it just hasn't run again yet. Trigger a manual run, or wait for the next scheduled one (see Triggering the Ingest).
  • Check whether the file is now sitting in 02-Processing, 04-Processed, or 99-Error – it may already have been picked up and moved.

"A file is stuck in 02-Processing"

This usually means a run was interrupted partway through. Check the Job Logs entry for that library and time – if the Status is Failed, see the Details column for the reason. If it stays stuck after the next run, contact your development team rather than moving the file yourself.

"A file ended up in 99-Error"

This means the file either failed data extraction or timed out waiting for a result. Review the file to check it's a valid, readable timesheet PDF. Once you've addressed the issue (or if you believe it was a temporary problem), move the file back into 01-Inbound and it will be picked up and retried on the next run.

"The Job Logs list shows Status: Failed"

This means the run for that library couldn't even start (e.g. a temporary SharePoint connectivity issue) – no files were processed at all, not even ones that would otherwise have succeeded. Check the Details column for the reason. If it happens repeatedly, contact your development/platform team.

"The Job Logs list shows Status: Partial Success"

Some files in that run succeeded and at least one failed. Check Details for which file(s) failed and why; the failed file(s) will be in 99-Error. The successful ones are unaffected and will already be in 03-Output/04-Processed.

"Does the application use my PDF Type / Site / Week No. values?"

No. Those columns are purely for your own organization and filtering of the document library – the application doesn't read them and processes files regardless of whether they're filled in. See Classifying Timesheet PDFs.

"How often does it run automatically?"

This depends on your environment's configuration and may not be the same everywhere. Check with your development/platform team, or judge it from the timestamps in the Job Logs list.

"I dropped a non-PDF file in 01-Inbound by mistake"

It's simply ignored – only files ending in .pdf are picked up. You can safely remove it.

"A row in Job Logs shows FilesProcessed = 0 and Details: No files found – is that a bug?"

No – this is expected and just confirms the run happened while that library's 01-Inbound was empty.
