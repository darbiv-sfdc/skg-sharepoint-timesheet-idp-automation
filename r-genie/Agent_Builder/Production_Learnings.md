> **V1.3.5 Fix (2026-04-23)**: User-reported cognitive anchoring bug. Every agent produced by Agent Builder was ending up with **~8 phases regardless of complexity**. Root cause: Agent Builder's OWN workflow is 8 phases (Goal → Architecture → RISEN+Phases → Rules → Examples → Docs → Validate → Register), and this "8-phase" label appears ~10 times across `Agent_Builder.mdc`, `README.md`, `INDEX.md`, `00_Phase_Orchestration.mdc`, and version history. The LLM absorbs "8 phases" as the dominant pattern in context and unconsciously proposes 8 for every target agent. Existing Complexity Assessment (Simple 4-5 / Medium 5-7 / Complex 7-10) was technically correct but lived only in an internal `<thinking>` block, never surfaced in the user-facing Architecture Proposal. Phase 2 "Phase Design" iteration also allowed unbounded `→ "add" to insert another phase` drift. Fix implemented as v1.3.5: (1) Architecture Proposal (Phase 1) now surfaces Complexity Tier + recommended range + phase-count justification + alternative sizing + explicit ANCHORING CHECK callout. (2) New **Phase Count Right-Sizing Rule** block after proposal: floor 3, ceiling 10, every phase maps to distinct deliverable + decision-value checkpoint, explicit "never 8 just because Agent Builder has 8". (3) Phase 2 split into **2B.i Phase Count Lock** (locks total before per-phase iteration) and **2B.ii Per-Phase Design** (only merge/split adjustments, no silent addition). (4) Two new SELF-CHECK items: PHASE-COUNT ANCHORING GUARD + PHASE DELIVERABLE GUARD. (5) Three new anti-pattern rows: default-to-8, incremental per-phase drift, unbounded "add" button. (6) Guidance §3 Phase Count few-shot expanded from 1B/1G to 2B/3G — BAD #2 explicitly shows the default-8 anchoring bug for a Simple-tier Terraform agent; GOOD #1/#2/#3 cover Simple/Medium/Complex tiers with rationale (GOOD #3 shows when 8 IS justified — the Cloud Success Architect). Self-observed during the Cloud Success Architect build itself — the agent was built with 8 phases partly due to this anchoring; retrospectively 6 phases would have been cleaner (Finalization and Panel Prep could have been checkpoints, not standalone phases).

> **V1.3.3 Fix (2026-04-23)**: User-driven cleanup based on two observations. (1) **Watermark was an Agent Builder extension, not a standard requirement**: `AGENT_ARCHITECTURE_STANDARD.md` does not mandate `watermark: "R-GENIE-CS150893"` in frontmatter. (2) **`sed -i ''` activation Step 1 fails frequently (Gap #15 manifestation)**: User observed that workflow activation Step 1 fails "most of the times and agents take different approach". Root cause is a textbook Gap #15 Tool Misuse Hazard: BSD vs GNU `sed` syntax drift (macOS needs `-i ''`, Linux needs bare `-i`), unconditional mass-toggle side effects on other agent lines, silent exit-0 failures when patterns don't match, and LLM preference for native `edit` tools over shell commands. Fix: replaced the sed pattern in the Agent Builder's activation skeleton (`skeleton-templates.md` §6) with a tool-first pattern using the native `edit` tool — atomic, platform-independent, verifiable diff. This is a future-facing fix; existing 15 workflow files under `.windsurf/workflows/use-XX-*.md` still use `sed` and are out-of-scope pending user confirmation for batch update.

> **V1.3.1 Fix (2026-04-23)**: Post-v1.3 review (prompted by user observation that LLMs often misuse shell commands for content mutation) identified that the Agent Builder had no behavioral gap entry for **Tool Misuse Hazard** — a production-observed failure mode where LLMs default to `sed`/`awk`/`cat >>`/`echo >>` for mutating `.mdc`/`.md`/`.yaml`/`.json` files instead of native `read_file`/`edit`/`multi_edit`/`write_to_file` tools.
